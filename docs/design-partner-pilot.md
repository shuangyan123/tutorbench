# Design Partner Pilot Boundary

Status: **private-pilot ready at the repository boundary**.

This document defines how TutorBench should handle an early design-partner
evaluation before any public benchmark, leaderboard, or customer-data pipeline
exists. The goal is to turn a partner's teaching policy into a small,
reproducible private scenario suite, run a baseline, return evidence-backed
Findings, and retest after the partner changes its Tutor.

This is an operational boundary, not a claim that TutorBench has completed a
real design-partner validation loop.

## What belongs in the public repository

The public repository may contain:

- provider-neutral contracts and runners;
- synthetic public scenario suites;
- the blank Scenario Intake template;
- anonymized or synthetic examples that contain no partner-confidential data;
- methodology describing how private pilots are performed;
- public evidence only after separate review and explicit authorization.

The public repository must not contain:

- raw production chat logs;
- private system prompts or commercial prompt text;
- partner credentials, API keys, cookies, tokens, or endpoint secrets;
- identifiable student or user data;
- production database exports;
- partner-internal policy documents unless they are explicitly approved for
  public release;
- raw provider payloads or hidden chain-of-thought;
- private pilot artifacts merely because they were generated by TutorBench.

These restrictions are additive to the repository rules in `AGENTS.md`.

## Default private workspace

Private pilot material should live outside tracked repository content. For a
local pilot, use an ignored path such as:

```text
data/private/design-partners/<partner-alias>/
├── intake/
├── suites/
├── policy/
└── notes/

artifacts/design-partners/<partner-alias>/
├── baseline/
└── candidate/
```

Both `data/private/` and `artifacts/` are ignored by the repository.

A separate private repository or controlled private storage is preferred when
multiple people need access. Do not make the public TutorBench repository the
source of truth for confidential partner material.

Use a partner alias in filenames and run IDs unless the partner has explicitly
approved public attribution.

## Minimum data rule

Collect the smallest amount of information needed to author and verify the
teaching decision.

Prefer this:

```text
Learner has tried the same algebra step twice.
On the third attempt, the Tutor should increase hint specificity without
giving the final answer.
```

over this:

```text
A copied production chat containing names, account metadata, internal prompts,
and unrelated conversation history.
```

Raw production examples are not required for the first pilot. A partner can
describe the situation, relevant learner state, decision boundary, and
unacceptable behavior in abstracted form.

If a real example is needed, the pilot owner must decide where it is stored,
who can access it, how it is anonymized or minimized, and whether it may ever
be transformed into a public synthetic scenario. TutorBench does not infer
publication permission from receiving the example.

## Scenario Intake -> private suite

Use [the Design Partner Scenario Intake template](design-partner-scenario-intake-template.md)
for each policy boundary.

The important distinction is:

```text
Tutor-visible context
  -> information the real Tutor is legitimately allowed to receive

Evaluator reference state
  -> authored truth used only to judge the Tutor
```

Do not copy evaluator truth, expected answers, rubric text, policy annotations,
or partner-internal diagnosis labels into the Tutor-visible input unless the
partner's production Tutor would actually receive that information.

Before a scenario is accepted into a private pilot suite, confirm:

1. the learner state and conversation history are sufficient to understand the
   decision point;
2. the expected teaching decision reflects the partner's stated policy rather
   than TutorBench's assumption;
3. acceptable alternatives are recorded where multiple responses are valid;
4. unacceptable behavior is observable and testable;
5. severity is justified by product impact, not by how much it changes a
   numeric score;
6. evaluator-only reference facts are supported by authored learner evidence;
7. confidential source material has not crossed into tracked public files.

## Running a private suite

The public `tutorbench health --suite` CLI currently selects registered public
suites. A private partner suite should therefore stay in a private harness and
use the stable package API rather than being copied into the public
`scenarios/` tree.

The package root exposes runtime validation for this purpose:

```ts
import { readFile, writeFile } from "node:fs/promises";
import {
  createHttpTutor,
  formatTutorHealthReport,
  parseTutorScenarioSuiteVNext,
  runTutorHealthEvaluation,
  writeTutorHealthReport,
} from "tutor-benchmark";

const suite = parseTutorScenarioSuiteVNext(
  JSON.parse(await readFile(process.env.PRIVATE_SUITE_PATH!, "utf8")),
);

const { evaluation, report } = await runTutorHealthEvaluation({
  suite,
  tutor: createHttpTutor({
    id: "partner-production",
    endpoint: process.env.PARTNER_TUTOR_ENDPOINT!,
  }),
  tutorDescriptor: {
    provider: "partner-alias",
    model: "production",
    promptVersion: "v17",
  },
  judge,
});

await writeFile(
  "artifacts/design-partners/partner-alias/baseline/evaluation.json",
  JSON.stringify(evaluation, null, 2) + "\n",
);
await writeTutorHealthReport(
  report,
  "artifacts/design-partners/partner-alias/baseline/health-report.json",
);
console.log(formatTutorHealthReport(report));
```

Credentials and private endpoint details remain in local environment variables
or the partner's existing secret store. They do not belong in suite JSON,
report artifacts, source control, or issue/PR text.

## Baseline -> change -> rerun

The minimum useful pilot is not a one-time score.

The target loop is:

```text
Partner teaching policy
  -> private authored scenarios
  -> baseline Tutor Health run
  -> evidence-backed Findings
  -> partner confirms which Findings are actionable
  -> partner changes prompt / policy / orchestration
  -> candidate rerun
  -> record resolved, persistent, and new Findings
```

Until an automated baseline/candidate comparison artifact exists, record the
comparison manually and keep both source evaluation artifacts.

A successful pilot signal is not "the score looks good." It is that at least
one Finding is credible enough to change the Tutor or its policy, and the same
scenario is rerun after that change.

## Provenance to preserve

Every baseline and candidate run should record enough identity to distinguish
the Tutor configuration without relying on filenames:

- partner alias;
- product surface;
- Tutor provider;
- Tutor model or deployment/config identifier;
- prompt or policy version;
- private suite ID and version;
- scoring profile ID and version;
- Judge provider/model identity when used;
- run date and run ID;
- baseline or candidate role.

Do not place API keys, private prompt bodies, raw provider responses, or
confidential endpoint URLs into provenance.

## Publication boundary

A private pilot remains private by default.

Publishing any partner name, scenario derived from confidential material,
model result, score, Finding, screenshot, case study, or before/after claim is
a separate action requiring explicit authorization and a privacy/content
review.

An anonymized statement such as "one design partner changed a tutoring policy
after a Finding" still counts as public evidence and must not be published
automatically.

## Claim limits

Private partner scenarios test whether a Tutor follows the authored policy at
specified decision points. They do not establish:

- general tutor competence;
- improved learning outcomes;
- causal effects on retention or mastery;
- representative production quality;
- calibrated confidence;
- universal teaching-policy correctness.

The partner owns the policy boundary. TutorBench owns the repeatable test and
the evidence trail.
