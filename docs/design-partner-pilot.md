# Design Partner Pilot Boundary

Status: **private-pilot ready at the repository boundary**.

This document defines how TutorBench should handle an early design-partner
evaluation before any public benchmark, leaderboard, or customer-data pipeline
exists. The goal is to turn a partner's teaching policy into a small,
reproducible private scenario suite, run a baseline, return evidence-backed
Findings, and retest after the partner changes its Tutor.

This is an operational boundary, not a claim that TutorBench has completed a
real design-partner validation loop.

## What belongs in the public repository

The public repository may contain:

- provider-neutral contracts and runners;
- synthetic public scenario suites;
- the blank Scenario Intake template;
- anonymized or synthetic examples that contain no partner-confidential data;
- methodology describing how private pilots are performed;
- public evidence only after separate review and explicit authorization.

The public repository must not contain:

- raw production chat logs;
- private system prompts or commercial prompt text;
- partner credentials, API keys, cookies, tokens, or endpoint secrets;
- identifiable student or user data;
- production database exports;
- partner-internal policy documents unless they are explicitly approved for
  public release;
- raw provider payloads or hidden chain-of-thought;
- private pilot artifacts merely because they were generated by TutorBench.

These restrictions are additive to the repository rules in `AGENTS.md`.

## Default private workspace

Private pilot material should live outside tracked repository content. For a
local pilot, use an ignored path such as:

```text
data/private/design-partners/<partner-alias>/
├── intake/
├── suites/
├── policy/
└── notes/

artifacts/design-partners/<partner-alias>/
├── baseline/
├── candidate/
└── comparison.json
```

Both `data/private/` and `artifacts/` are ignored by the repository.

A separate private repository or controlled private storage is preferred when
multiple people need access. Do not make the public TutorBench repository the
source of truth for confidential partner material.

Use a partner alias in filenames and run IDs unless the partner has explicitly
approved public attribution.

## Minimum data rule

Collect the smallest amount of information needed to author and verify the
teaching decision.

Prefer this:

```text
Learner has tried the same algebra step twice.
On the third attempt, the Tutor should increase hint specificity without
giving the final answer.
```

over this:

```text
A copied production chat containing names, account metadata, internal prompts,
and unrelated conversation history.
```

Raw production examples are not required for the first pilot. A partner can
describe the situation, relevant learner state, decision boundary, and
unacceptable behavior in abstracted form.

If a real example is needed, the pilot owner must decide where it is stored,
who can access it, how it is anonymized or minimized, and whether it may ever
be transformed into a public synthetic scenario. TutorBench does not infer
publication permission from receiving the example.

## Scenario Intake -> private suite

Use [the Design Partner Scenario Intake template](design-partner-scenario-intake-template.md)
for each policy boundary.

The important distinction is:

```text
Tutor-visible context
  -> information the real Tutor is legitimately allowed to receive

Evaluator reference state
  -> authored truth used only to judge the Tutor
```

Do not copy evaluator truth, expected answers, rubric text, policy annotations,
or partner-internal diagnosis labels into the Tutor-visible input unless the
partner's production Tutor would actually receive that information.

Before a scenario is accepted into a private pilot suite, confirm:

1. the learner state and conversation history are sufficient to understand the
   decision point;
2. the expected teaching decision reflects the partner's stated policy rather
   than TutorBench's assumption;
3. acceptable alternatives are recorded where multiple responses are valid;
4. unacceptable behavior is observable and testable;
5. severity is justified by product impact, not by how much it changes a
   numeric score;
6. evaluator-only reference facts are supported by authored learner evidence;
7. confidential source material has not crossed into tracked public files.

## Running a private suite

Freeze the private Pilot Spec, complete each Scenario Intake, and preserve the
resulting Scenario vNext `suite.json` in private storage. The CLI reads local
JSON and validates it with `parseTutorScenarioSuiteVNext` before Tutor execution:

```sh
tutorbench health \
  --http "$PARTNER_TUTOR_ENDPOINT" \
  --suite-file data/private/design-partners/partner-alias/suites/suite.json \
  --tutor-provider partner-alias \
  --tutor-model production \
  --prompt-version v17 \
  --output artifacts/design-partners/partner-alias/baseline
```

`--suite-file` and `--suite` are mutually exclusive; both `--flag value` and
`--flag=value` work. Omitting both retains the default registered public suite.
The private file is never registered, copied into `scenarios/`, or uploaded.
Tutor-visible context is still sent to the selected HTTP Tutor, and selecting
a Judge still sends the existing Judge input through that provider boundary.
Private file read/JSON/schema errors do not echo file contents or paths.

The required `--tutor-provider`, `--tutor-model`, and `--prompt-version` values
are short provenance labels (at most 300 characters), never secrets or prompt
bodies. Add one existing Judge flag (`--judge-openai`, `--judge-deepseek`, or
`--judge-chat-completions`) when configured and authorized. Without a Judge,
Judge-owned checks remain unresolved and the command exits `2` unless an
existing gate/HTTP failure requires `1`. A Judge-backed gate pass exits `0`.
Writing a manifest does not make incomplete evidence complete.

Each completed artifact write produces `evaluation.json`, `health-report.json`,
`health-report.txt`, and `pilot-run-manifest.json`, including runs that report
failure or unresolved evidence. The three existing artifact formats are unchanged.
The suite snapshot itself remains caller-owned; preserve it separately.
The package APIs remain available for custom private harnesses.

Use a different output directory for baseline and candidate. Following the
comparison writer's exclusive-create convention, `health` refuses any existing
file, directory, or symlink at one of the four artifact names before provider
execution. Other files in the directory remain untouched. It serializes and
validates all output before writing, uses exclusive creates, and writes the
manifest last. On a caught write failure it removes only files created by that
attempt; cleanup failure is reported. This is not a filesystem transaction:
process termination can leave a partial set, and completed Tutor/Judge calls
cannot be undone. Inspect incomplete output before retrying; retrying may call
providers again. A new directory avoids overwriting earlier private evidence.

Credentials and private endpoint details remain in local environment variables
or the partner's existing secret store. They do not belong in suite JSON,
report artifacts, source control, or issue/PR text.

For customer-facing reporting, use the [Design Partner Report Data Map](design-partner-report-data-map.md) to keep report fields traceable to the private suite, TutorEval evaluation artifact, and Tutor Health report without creating a second reporting truth.

## Baseline -> change -> rerun

The minimum useful pilot is not a one-time score.

The target loop is:

```text
private Pilot Spec
  -> per-scenario Intake
  -> private suite.json
  -> tutorbench health --suite-file ...
  -> baseline artifacts + run manifest + evidence-backed Findings
  -> partner changes Tutor
  -> candidate run with the frozen suite and a new output directory
  -> tutorbench health-compare
  -> resolved / persistent / new / unresolved
```

Keep the frozen suite and both runs' source artifacts and manifests. Rerun the
health command with the candidate's declared prompt/configuration version and
`--output artifacts/design-partners/partner-alias/candidate`. After
the rerun, create the canonical, versioned comparison without calling either
provider or modifying the source artifacts:

```sh
tutorbench health-compare \
  --baseline artifacts/design-partners/partner-alias/baseline \
  --candidate artifacts/design-partners/partner-alias/candidate \
  --baseline-suite data/private/design-partners/partner-alias/suites/suite.json \
  --candidate-suite data/private/design-partners/partner-alias/suites/suite.json \
  --output artifacts/design-partners/partner-alias/comparison.json
```

Each run directory contains `evaluation.json` and `health-report.json`. Use each
run's preserved suite path if they were stored separately. Output must be a new
file. The command prints a concise summary and writes deterministic JSON.
When a source directory contains `pilot-run-manifest.json`, it verifies the
manifest against that suite and the exact evaluation/report bytes before
comparison. Invalid or mismatched manifests fail closed. Historical directories
without a manifest retain the existing comparison behavior.
Exit `0` means comparable evidence (even if Findings are new or persistent),
`2` means unresolved evidence, and `1` means invalid/non-comparable sources or
an I/O error. This is not an automatic regression threshold or release gate.

The package API exposes `compareTutorHealthRuns({ baseline, candidate })`, where
each input contains `{ suite, evaluation, report }`, plus
`parseTutorHealthComparison`, `isTutorHealthComparison`,
`assertValidTutorHealthComparison`, `formatTutorHealthComparison`, and
`writeTutorHealthComparison`. The writer also refuses to overwrite any existing
file. See the [comparison contract and evidence rules](design-partner-report-data-map.md#before--after-tracking).

A successful pilot signal is not "the score looks good." It is that at least
one Finding is credible enough to change the Tutor or its policy, and the same
scenario is rerun after that change.

## Provenance to preserve

Every baseline and candidate run should record enough identity to distinguish
the Tutor configuration without relying on filenames:

- partner alias;
- product surface;
- Tutor provider;
- Tutor model or deployment/config identifier;
- prompt or policy version;
- private suite ID and version;
- scoring profile ID and version;
- Judge provider/model identity when used;
- run date and run ID;
- baseline or candidate role.

Do not place API keys, private prompt bodies, raw provider responses, or
confidential endpoint URLs into provenance.

`pilot-run-manifest.json` uses `kind: "tutor-health-run-manifest"`,
`schemaVersion: 1`, and `provenance: "local_execution_only"`. It binds suite
ID/version and canonical SHA-256, evaluation run/evaluator identity and byte
SHA-256, report schema version and byte SHA-256, bounded Tutor/Judge descriptors,
and runs per case. See the [manifest data map](design-partner-report-data-map.md#local-run-manifest)
for exact hashing and validation semantics.

This is local execution provenance, not cryptographic attestation of the
external Tutor's actual model, prompt, deployment, or configuration. A caller
can rewrite both source artifacts and manifest; preserve originals in controlled
private storage. It does not grant publication permission or establish real
design-partner validation. That real evidence loop remains pending.

## Publication boundary

A private pilot remains private by default.

Publishing any partner name, scenario derived from confidential material,
model result, score, Finding, screenshot, case study, or before/after claim is
a separate action requiring explicit authorization and a privacy/content
review.

An anonymized statement such as "one design partner changed a tutoring policy
after a Finding" still counts as public evidence and must not be published
automatically.

## Claim limits

Private partner scenarios test whether a Tutor follows the authored policy at
specified decision points. They do not establish:

- general tutor competence;
- improved learning outcomes;
- causal effects on retention or mastery;
- representative production quality;
- calibrated confidence;
- universal teaching-policy correctness.

The partner owns the policy boundary. TutorBench owns the repeatable test and
the evidence trail.
